# Network Interconnectivity (Expert Practical)

# VPC Peering 심층 분석

## 1. VPC Peering이란?

**VPC Peering**은 서로 다른 두 VPC 간에  
인터넷을 거치지 않고 AWS Private Backbone을 통해  
직접 트래픽을 라우팅하는 네트워크 연결 서비스이다.

특징:

- 고속 통신
- 프라이빗 연결
- 기본적인 VPC 간 연결 방식

---

# 2. VPC Peering 3대 핵심 원칙

## ① No Overlapping CIDR

두 VPC의 CIDR이 단 1개의 IP라도 겹치면  
피어링 생성이 불가능하다.

예:

VPC-A: 10.1.0.0/16  
VPC-B: 10.1.1.0/24  

→ 겹침 발생 → 생성 불가

따라서 사전 IP 설계(IP Addressing Plan)가 필수이다.

---

## ② Non-Transitive Routing (전이적 라우팅 불가)

A ↔ B  
B ↔ C  

라고 해서  

A ↔ C 가 자동으로 연결되지 않는다.

A와 C가 통신하려면  
별도의 A-C 피어링을 맺어야 한다.

---

## ③ Cross-Region / Cross-Account 지원

- 다른 리전 가능 (서울 ↔ 도쿄)
- 다른 AWS 계정 가능
- 다른 회사 계정과도 연결 가능

---

# 3. 실무 예제 1: 기본 1:1 피어링 (동일 계정/리전)

구조:

App VPC (10.1.0.0/16)  
↕  
DB VPC  (10.2.0.0/16)

필수 작업 3가지:

1. Peering 생성
2. App 라우팅 테이블 수정
3. DB 라우팅 테이블 수정

## Terraform 코드

```hcl
# 1. Peering 생성
resource "aws_vpc_peering_connection" "app_to_db" {
  vpc_id      = aws_vpc.app_vpc.id
  peer_vpc_id = aws_vpc.db_vpc.id
  auto_accept = true

  tags = { Name = "Peering-App-to-DB" }
}

# 2. App → DB 라우팅
resource "aws_route" "app_to_db_route" {
  route_table_id            = aws_route_table.app_rt.id
  destination_cidr_block    = aws_vpc.db_vpc.cidr_block
  vpc_peering_connection_id = aws_vpc_peering_connection.app_to_db.id
}

# 3. DB → App 라우팅
resource "aws_route" "db_to_app_route" {
  route_table_id            = aws_route_table.db_rt.id
  destination_cidr_block    = aws_vpc.app_vpc.cidr_block
  vpc_peering_connection_id = aws_vpc_peering_connection.app_to_db.id
}

4. 실무 예제 2: Cross-Region Peering

서울(ap-northeast-2) ↔ 도쿄(ap-northeast-1)

핵심 차이점:

auto_accept 사용 불가

Provider Alias 필요

수락자 리소스 별도 작성

Terraform
# Provider 설정
provider "aws" {
  region = "ap-northeast-2"
}

provider "aws" {
  alias  = "tokyo"
  region = "ap-northeast-1"
}

# 서울에서 요청
resource "aws_vpc_peering_connection" "seoul_req" {
  vpc_id      = aws_vpc.seoul_vpc.id
  peer_vpc_id = aws_vpc.tokyo_vpc.id
  peer_region = "ap-northeast-1"
}

# 도쿄에서 수락
resource "aws_vpc_peering_connection_accepter" "tokyo_acc" {
  provider                  = aws.tokyo
  vpc_peering_connection_id = aws_vpc_peering_connection.seoul_req.id
  auto_accept               = true
}
5. Non-Transitive Routing 예시

허브 앤 스포크 구조:

   VPC A (Mgmt)
   /           \

VPC B VPC C

A ↔ B 가능
A ↔ C 가능
B ↔ C 불가능

해결 방법:

B-C 직접 피어링

AWS Transit Gateway 사용

6. 확장성 문제 (Full Mesh)

공식:

N*(N-1)/2

예:

VPC 3개 → 3개 피어링
VPC 5개 → 10개 피어링
VPC 10개 → 45개 피어링

VPC 4~5개 이상이면
Transit Gateway로 전환 고려.

7. 과금 주의사항

피어링 생성 자체는 무료.

하지만 데이터 전송 요금 발생:

같은 리전 AZ 간 → GB당 $0.01

교차 리전 → 더 비쌈

대규모 데이터 이동 시 요금 주의.

8. 보안 그룹 제약
동일 리전

상대방 VPC의 Security Group ID 직접 참조 가능.

예:

source = sg-1234abcd

교차 리전

Security Group ID 참조 불가.
상대방 CIDR 전체를 열어야 함 → 보안 취약 가능성 존재.

9. 핵심 용어
Provider Alias

Terraform에서 다른 리전/계정을 제어하기 위한 별칭.

CIDR

네트워크 범위를 정의하는 방식.
예: 10.1.0.0/16

Full-Mesh

모든 노드가 서로 직접 연결된 구조.
확장성 낮음.

10. 아키텍트 관점 정리

VPC 2~3개 → Peering OK
VPC 5개 이상 → Transit Gateway 고려
VPC 10개 이상 → Transit Gateway 필수

시험 핵심 요약

CIDR 겹치면 Peering 불가

전이적 라우팅 불가

Cross-Region 가능

Full Mesh는 확장성 문제 발생

대규모 환경은 Transit Gateway 사용
